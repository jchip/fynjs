# Docs site plan

Plan to replace the old docs with one site for the whole monorepo. Commit `e918e035` removed the
root Docusaurus 2 site. This plan finishes the cleanup in each package and then builds the new
site.

## Goals

1. Guides are written in plain Markdown.
2. API reference is generated by TypeDoc, the tool `xaa`, `cli-args` and others already use.
3. All docs live in one top-level `docs/` dir.
4. The site builds only from the `cf-pages` branch and publishes to Cloudflare Pages.

## Phase 2: site skeleton

Recommended stack: **VitePress + TypeDoc with `typedoc-plugin-markdown`**.

- VitePress is Markdown-first and has a small dependency tree. The old Docusaurus build had
  about 190 audit advisories. Docusaurus 3 is the fallback if we want its plugin ecosystem.
- `typedoc-plugin-markdown` makes TypeDoc emit Markdown instead of HTML. The API pages then
  share one theme, nav and search with the guides.
- TypeDoc runs once at the top level with `entryPointStrategy: "packages"`. Each package sets
  its own entry point in a small `typedoc.json`.

Layout:

```
docs/
  package.json          private, own deps (vitepress, typedoc, plugin)
  typedoc.json          lists the packages to document
  .vitepress/config.ts  nav and sidebar
  index.md              landing page
  guide/                hand-written guides
  packages/<name>/      per-package overview, pulled from each README
  api/                  generated by TypeDoc, gitignored
```

`docs/` must be excluded from fynpo's package auto-search, the same way `docusaurus` was. This
keeps its deps out of the monorepo install.

Verify: `xrun docs:build` in `docs/` produces a static site locally. Spot-check API pages for
`xaa`, `cli-args` and `fynpo-base` against the old HTML.

## Phase 3: content

2. One overview page per published package, sourced from its README.
3. Move `fyn/docs/*.md` into `docs/guide/fyn/`.
4. Link `run-verify/docs/reference.md` from the site. Copy it at build time so the npm copy

5. Repoint the 7 `jchip.github.io` README links to the new domain.

Start with the TypeScript packages that already had API docs. Add the rest after that.

## Phase 4: `cf-pages` branch and Cloudflare Pages

`main` holds the docs source. The `cf-pages` branch is the only place a docs build runs. Main
CI never builds docs.

Recommended flow:

1. Push or fast-forward `main` into `cf-pages` when we want to publish.
2. A GitHub Actions workflow runs on push to `cf-pages`. It installs with fyn, builds the
   packages TypeDoc needs, builds the site, and runs `wrangler pages deploy`.
3. Secrets: `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.

Why Actions instead of Cloudflare's own Git build: TypeDoc needs the monorepo installed so it
can resolve types across packages. That needs fyn. Our CI already sets fyn up. Cloudflare's
build image does not.

Verify: a push to `cf-pages` deploys a preview URL. API pages resolve cross-package types.

## Open decisions

1. **Site tool.** VitePress (recommended) or Docusaurus 3.
2. **Build runner.** GitHub Actions + `wrangler` (recommended) or Cloudflare's Git build.
3. **`cf-pages` content.** Mirror of `main` that gets built (recommended), or an orphan branch
   that holds only the built output.
4. **Domain.** Cloudflare's `*.pages.dev` default or a custom domain. This decides the URL used
   in phase 3 step 5.
5. **API scope.** All 34 packages, or only the ones with a public API worth documenting.
